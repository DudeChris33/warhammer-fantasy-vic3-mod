# Warhammer Fantasy Overhaul

A total-conversion mod for Victoria 3 (supported game version 1.13.9), reskinning the base game into the Warhammer Fantasy setting using Clausewitz script (`.txt`), the PDX GUI format (`.gui`), and localization YAML (`.yml`). Multiplayer-synchronized (`.metadata/metadata.json`), so scripted content must stay deterministic across clients.

## Canonical entry point

`docs/*.log` are game-generated reference dumps and are the authority on what script syntax is valid — read the relevant one before writing any script that uses it:

| File | Covers |
|---|---|
| `docs/effects.log` | All valid effects |
| `docs/triggers.log` | All valid triggers/conditions |
| `docs/modifiers.log` | All valid static modifiers |
| `docs/event_targets.log` | Scope-linking event targets |
| `docs/on_actions.log` | Game-fired on_action hooks |
| `docs/custom_localization.log` | Custom localization definitions |

These are read-only references generated by the game itself — never hand-edit them.

## Vanilla game files

The unmodded Victoria 3 install is on disk and is the authority on what this mod is
actually overhauling — the shape of the data this mod replaces, the file formats, the
naming conventions, and what a "normal" entry looks like. **Read the vanilla file
before authoring its mod counterpart.** Where `docs/*.log` says what syntax is legal,
vanilla says what real, shipped content looks like.

```
C:\Program Files (x86)\Steam\steamapps\common\Victoria 3\game
```

Its layout mirrors this mod's: `common/` (135 database subfolders), `events/`, `gui/`,
`interface/`, `gfx/`, `localization/english/`, `map_data/`, `music/`, `sound/`. Notably
useful:

| Vanilla path | Why it matters here |
|---|---|
| `game/map_data/` | `default.map`, `provinces.png`, `heightmap.png`, `rivers.png`, `province_terrains.txt`, `adjacencies.csv` — the exact formats, sizes and conventions this mod's `map_data/` must match |
| `game/map_data/state_regions/` | 18 files defining every vanilla state — the reference for state-region syntax, province-id hex lists, hubs, arable land, resources |
| `game/common/<db>/` | The canonical example set for any database before authoring the mod's version of it |
| `game/localization/english/` | Vanilla key names — needed to know what `localization/replace/english/` must override |

This install is **read-only**: never edit, never write, never stage anything from it.

A private, read-only GitHub mirror of this same vanilla `common/`, `events/`, `localization/` and `map_data/` tree also exists for machines where the Steam install above isn't reachable (used to confirm the `common/cultures` schema for epic #3404's Old World cultures). Ask the user for its URL when needed — it is not part of this repo and nothing from it should be committed here.
Copy what's needed into this mod folder and modify the copy.

| `music/`, `sound/` | Audio assets |

| `docs/` | Read-only game-generated script reference (see above) |
| `planning/` | Review-panel targets, backlog/rejected notes, and the maestro skills' gitignored `.cache/` scratch — not the primary tracker (the maestro board is; see below) |
| `tools/` | Offline map generator + validator toolchain (Python — Pillow/numpy/scipy/scikit-image). Includes the **source-driven ingestion stage**: reference imagery lives in a repo-root `sources/` folder — committed in full via Git LFS as of 2026-09-03 (user decision: private repo, not worth manually shifting ~2.3GB between devices); `tools/SOURCES.md` (a SHA-256 manifest) and `tools/registration/*.json` (how each source maps onto the canvas) remain the provenance record alongside it. That stage feeds `tools/generate_coastline_mask.py` / `tools/generate_heightmap.py` / `tools/generate_rivers.py` / `tools/generate_state_labels.py` / `tools/generate_sea_zones.py` / `tools/generate_provinces.py`, which write the committed, generated `tools/derived/land_sea_mask.png` (the coastline authority — flood-filled by `generate_coastline_mask.py` from the user's traced coastline in `sources/land_sea_mask.png`, or, with its `--from-fill` mode, read directly when that source is already a finished black/white land fill rather than a trace to flood-fill; *consumed* by everything downstream, never re-derived; user decision 2026-08-22 deleted the old height-ramp mask derivation that lived in `generate_heightmap.py`) / `map_data/heightmap.png` / `map_data/rivers.png` (+ `tools/derived/state_labels.png`, and `tools/derived/sea_zones.png` + `tools/derived/sea_zones_index.json` — the sea-zone label layer flood-filled from the user's hand-drawn purple boundary network, keyed on the vanilla 3000+ sea-state id band, decoupled from `state_labels.png` for now) — regenerate via those scripts, never hand-edit the bitmaps. `generate_provinces.py` (board #2773) writes `map_data/provinces.png` (8192x3616 RGB, the first-pass whole-world province image, Git-LFS-tracked) + `tools/derived/provinces_index.json` (per-province id/colour/area/coastal/impassable/placeholder) + `tools/derived/land_regions_index.json` (board #2928 — the region→province grouping `subdivide` already computes, region-keyed with each cell carrying `region`/`kind`/`area`/`provinces`; the land mirror of `sea_zones_index.json`, feeding land state-region emission in #2930): `tools/worldgen/land_provinces.py` — the land mirror of `worldgen/sea_zones.py`, likewise decoupled from `state_labels.png` — flood-fills the user's hand-drawn magenta state-region network (`sources/terraqueous_globe_reprojected - state_regions.png`) into barrier-respecting regions and subdivides each drawn region into land provinces `1..N` (no province crosses a magenta line; a far continent that shares the Old World's landmass but carries no interior magenta is classified an out-of-scope placeholder by interior-magenta density and kept whole as one passable placeholder province — Vic3 stacks every hub on one province, so a landmass needs only one passable province to boot as a legal state), and `generate_provinces.py` folds those together with the already-committed sea zones `N+1..N+M`. `subdivide` returns that province→region grouping as its third value (`reg_of`); the generator inverts it into `land_regions_index.json` and asserts totality (every land province in exactly one region) before writing, leaving `provinces.png`/`provinces_index.json` byte-identical. `tools/render_provinces_preview.py` is the matching local-only review render (`tools/derived/`, gitignored). `tools/generate_sea_regions.py` (board #2929) is the sea-side **emitter**: it joins `provinces_index.json` (the colour authority — sea-zone label `s` ↔ province cell `label == land_provinces + s`) with the canon `sea_zones_index.json` (`key`/`id`/`display_name`/`sea_group`) and writes the four real game files — `map_data/state_regions/99_seas.txt` (one passable `STATE_* { id provinces }` block per zone, colours from `provinces.png`), an in-place block-replace of only `map_data/default.map`'s `sea_starts` body (every other key left untouched), `common/strategic_regions/water_strategic_regions.txt` (one `states`-only region per `sea_group`, filename overrides vanilla's dangling file), and a header-only `map_data/adjacencies.csv` when absent (straits are a later user-driven pass on the rendered map) — plus the committed sea loc `localization/english/map/wh_seas_l_english.yml`. It no longer stages `tools/derived/seas_99_seas.txt` / `seas_sea_starts.txt` (deleted — they were mis-coloured by an independent allocator). Registration records are **machine-fitted** by `tools/fit_registration.py` from the hand-authored seeds in `tools/registration/seeds/` (an explicit authoring action, like `--update-manifest`); re-derive rather than hand-edit them. `tools/config/inland_lakes.json` is likewise hand-authored geographic data — the keep-list of genuine enclosed lakes/seas (by interior seed pixel) that the old height-ramp mask derivation read to tell them apart from false enclosed water (drawn rivers, flooded marshes). **As of 2026-08-22 nothing reads it**: the sole owner of the mask, `generate_coastline_mask.py`, classifies enclosed seas as water by pure coastline parity (no lake list), so this file (and `schema.load_inland_lakes`) is currently orphaned pending a decision to keep or retire it. The `tools/` scripts themselves are **not loaded by the game**; kept out of mod content folders. Run `tools/validate_map.py` (`--province-bitmap` for the current province-bitmap stage, `--sea` for the sea engine files emitted by `generate_sea_regions.py`) + `tools/worldgen/sources.py --verify` before committing map data; see `tools/MAP_RUNBOOK.md` for the desktop-client steps. |

**`common/` folder loading is governed by `.metadata/metadata.json`'s `replace_paths` list.** A folder listed there is *blanked*: the game does not load vanilla's files for it at all, so every definition that folder normally provides must be re-authored (cleaned-generic or WH-native) in this mod's copy, or it simply doesn't exist — this is what epic #3292's restoration work is for. A folder **not** listed there merges normally: vanilla's files for it still load exactly as shipped, and this mod only needs a file there if it wants to *override or add to* that content. **Do not assume a `common/<folder>` that's empty or absent in this repo is a gap needing restoration — check `replace_paths` first.** If the folder isn't listed, vanilla content already resolves and no action is needed unless a fresh `error.log` proves otherwise (board item #3435 hit exactly this: `combat_unit_groups`/`combat_unit_experience_levels` looked like the same class of gap as scripted_triggers, but neither is in `replace_paths`, so vanilla's generic definitions likely already load fine).

Most `common/*` and top-level content folders still contain only `.gitkeep`. Authored so far: `map_data/`, which also holds `heightmap.png`, `rivers.png` and `provinces.png` generated by the `tools/` pipeline described above (not hand-authored — regenerate via the scripts, don't edit the bitmaps directly); and the culture foundation (board item #3405, epic #3404) — `common/discrimination_trait_groups/` (19 heritage/language/religious-heritage groups), `common/discrimination_traits/` (32 heritage/language traits), and `common/religions/` (18 religions), with their 69 display-name keys in `localization/english/culture_foundation_heritages_l_english.yml`, `culture_foundation_languages_l_english.yml` and `culture_foundation_religions_l_english.yml`. On top of that foundation, epic #3404's Old World cultures (board items #3406-#3409) have authored 31 cultures across 9 of the 20 `common/cultures/NN_<region>.txt` files (`00_norsca.txt`, `01_kislev.txt`, `02_empire.txt`, `03_brettonia.txt`, `04_karaz_ankor.txt`, `05_southern_realms.txt`, `06_badlands.txt`, `07_nehekhara.txt`, `10_dark_lands.txt`; the remaining region files are still placeholders), each with color/religion/heritage/language/traditions/obsessions/name-lists/ethnicities/graphics — see `.claude/rules/scripting.md` for the entry schema. Each culture also registers three modifier types in `common/modifier_type_definitions/culture_cultural_acceptance_modifier_types.txt`, `culture_fervor_target_modifier_types.txt` and `culture_standard_of_living_modifier_types.txt`, and six paired static modifiers in the matching `common/static_modifiers/culture_*_modifiers.txt` files. Loc lives in per-region `localization/english/cultures_<region>_l_english.yml` files plus one shared, append-only `cultures_names_l_english.yml` for per-name display keys (deduplicated against vanilla's own name keys).

## How to work here

- **Rules** in `.claude/rules/*.md` are loaded automatically. Follow them.
- **Skills** in `.claude/skills/` invoked with `/<name>`. Work tracking runs on
  the **maestro board** (via the maestro MCP), not local files — the board item's
  markdown "workspec" is the work record:
  - `/maestro-task <description>` — explore, clarify, file work item(s) onto the board (stage=inbox)
  - `/maestro-scope <item-ids>` — scope item(s) in-repo, append a `## Plan`, push back (stage=planned)
  - `/maestro-build <item-ids>` — claim, execute the plan with full build discipline, land at review/done
  - `/maestro-auto <item-ids>` — scope + build in one mostly-autonomous run, one approval gate
  - `/maestro-vibe <description>` — vibe-code a small change with build discipline, no board ceremony
  - `/maestro-release-note` — draft the next release note from the actual diffs
  - `/sites-verify <url>` — actually look at a deployed maestro site (real pixels)
  - `/review-panel <target>` — convene the five-expert review panel on a plan, a diff, or a rendered artifact
  - `/project-memory` — show memory state

  First run in this repo needs a `.claude/maestro.json` (`{"workspace", "board"}`)
  — the maestro skills prompt to create it if it's missing.
- **Memory is cross-device via maestro knowledge.** This project is worked from
  multiple machines. Claude Code's own memory (`~/.claude/projects/.../memory/`,
  per user/feedback/project/reference — see the memory-system instructions in the
  system prompt) lives on one machine only and does not follow the repo. Whenever
  you save one of those memories, also call the maestro MCP's `add_knowledge`
  (project id in `.claude/maestro.json`) with the same content, so it is visible
  from every device. Map memory `type` to knowledge `kind`: `feedback` → `rule`,
  `project` → `decision` (or `pattern`/`reference` when that fits the content
  better), `reference` → `reference`, `user` → `rule`. Before trusting a
  cross-device fact, prefer `search_knowledge` (workspace/project-wide) over the
  local memory files, since the local files may be stale or absent on the current
  machine.
- **Sub-agents** in `.claude/agents/`:
  - Spawned by `/maestro-build`, `/maestro-auto` and `/maestro-vibe` after a build:
    - `docs-updater` — update docs from diff
    - `security-review` — review diff for MP-desync and content-integrity risks
  - Spawned by `/review-panel` (read-only reviewers; they never edit):
    - `loremaster` — Warhammer Fantasy canon: names, places, factions, era, tone
    - `cartographer` — map craft: shapes, borders, projection, legibility
    - `geographer` — physical plausibility: elevation, climate, coasts, rivers
    - `vic3-modding-expert` — engine correctness: script, formats, loc, determinism
    - `game-designer` — play and scope: granularity, systems fit, sequencing

## Workflow chain

Work tracking is the **maestro board**, not local `planning/` files. The item's
markdown workspec carries the spec (and the `## Plan` scoping appends); its stage
column and activity trail carry state and progress.

```
Bug or feature idea
      │
      ▼
/maestro-task   ── files ──►  board item, stage=inbox (the workspec)
      │
      ▼
/maestro-scope  ── appends ─►  ## Plan on the workspec, stage=planned
      │
      ▼
/maestro-build  ── executes ─►  commits + activity trail, stage=review/done
```

`/maestro-scope` must never be skipped — it's where file-level decisions get
pinned down. `/maestro-auto` runs scope + build as one approval-once run;
`/maestro-vibe` is the lightweight path for a change too small to track (no board
ceremony, a born-done history item at close-out).

`/review-panel` is optional and can run at any point — most usefully on a `## Plan`
before a build commits to it, and on the rendered artifact once one exists. It
reads planning files, a diff, or a rendered artifact; it never edits mod content.
Its ruling is advisory: on anything visual the user is the final gate.

`planning/` remains for `/review-panel` targets, backlog/rejected notes, and the
maestro skills' gitignored `planning/.cache/` scratch — not the primary tracker.

## Autonomy model

The generation/iteration loop is where to run long and unattended; sourcing and the
visual verdict are where to stop and hand back. Don't invert this — the failures on
this project have come from stopping too early inside the loop (at an offline-green
checkpoint) and from trying to own the two ends that are the user's.

**Run autonomously, without pausing for approval, inside the tooling loop:** edit a
generator / LUT / `tools/registration/seeds/` / `tools/config/inland_lakes.json`, then
re-derive (`fit_registration.py`, `generate_heightmap.py`, `generate_rivers.py`,
`generate_state_labels.py`) → run the full offline gate in
[testing.md](.claude/rules/testing.md) (`sources.py --verify`, `validate_map.py [--labels]`,
`run_fixture.py --check`) → **render the map and send the PNG** → read it, diagnose,
and go again. Iterate this loop to convergence on your own; a green offline gate is a
precondition to continue, never a stopping point. Chain several regen→render passes in
one turn rather than surfacing after each.

**Always stop and hand back to the user for:**

- **Sourcing.** Choosing, adding, swapping, or marking up imagery in `sources/` is the
  user's — it's third-party IP tracked only by SHA manifest, and better source beats
  more tuning. If a result is capped by the source, say so and ask for imagery; do not
  browse for or substitute your own. `--update-manifest` follows a user source change,
  never precedes one.
- **The visual verdict.** On any rendered map the user is the final gate. Render, send,
  and state what you see and what you'd change — then wait for accept/reject. Never
  bank a map as done, and never commit map bitmaps, on offline checks alone; the
  rendered artifact is the real gate (this is the lesson that keeps recurring).
- **Irreversible or scope-widening steps** already fenced elsewhere: `git commit` only
  when the loop has converged and the user has accepted the visual; `git push`, new
  top-level folders, and anything the Non-negotiables list forbids.

When a request is loop-shaped ("get the coastline right", "fix the enclosed water"),
treat it as: iterate the tooling loop to convergence, render, and return with the PNG
plus a recommendation — not as a single edit-then-ask cycle.

## Trust order

On conflict, in this order: `docs/*.log` (what the game engine actually accepts) → the vanilla install at `.../Victoria 3/game/` (what shipped content actually does) → `.claude/rules/` → existing script patterns already committed in `common/`/`events/`. Fix the losing side and update it to match.

## Build + test

There is no compiler and no automated test suite — Clausewitz script has no offline validator. Validation is: load the mod in Victoria 3 and check `../../logs/error.log` (relative to this mod folder, i.e. `Documents/Paradox Interactive/Victoria 3/logs/error.log`) for script/loc parse errors after every change that touches `common/`, `events/`, `gui/`, `localization/`, or `map_data/`. Treat any new line in that log referencing this mod's files as a build failure. `map_data/` changes additionally get an offline pre-commit lint first — see `.claude/rules/testing.md`.

## Non-negotiables

- Read before editing — always check `docs/*.log` for the exact effect/trigger/modifier signature before using it, and read the vanilla file at `.../Victoria 3/game/` that this mod's file overrides or parallels.
- Never write to the vanilla install (`C:\Program Files (x86)\Steam\steamapps\common\Victoria 3\game`) — it is read-only reference. Copy into this mod folder and edit the copy.
- No drive-by refactors — don't touch unrelated files or folders.
- No `git add -A` — stage specific files only.
- No `git push` unless asked.
- Never hand-edit files in `docs/` — they're generated by the game, not authored.
- Never hand-edit generated map bitmaps (`map_data/heightmap.png`, `map_data/rivers.png`, `map_data/provinces.png`, `tools/derived/land_sea_mask.png`, `tools/derived/state_labels.png`, `tools/derived/sea_zones.png`) — they're written by `tools/generate_coastline_mask.py` (the sole owner of `land_sea_mask.png`) / `tools/generate_heightmap.py` / `tools/generate_rivers.py` / `tools/generate_state_labels.py` / `tools/generate_sea_zones.py` / `tools/generate_provinces.py`; fix the source/LUT/registration data and regenerate. Likewise `tools/registration/*.json`, `tools/derived/COVERAGE.md`, `tools/derived/sea_zones_index.json`, `tools/derived/provinces_index.json` and `tools/derived/land_regions_index.json` — re-derive with `tools/fit_registration.py` / the generator, don't hand-edit. The sea engine files `map_data/state_regions/99_seas.txt` and `common/strategic_regions/water_strategic_regions.txt` are emitted by `tools/generate_sea_regions.py` — regenerate, never hand-edit. `map_data/default.map` is **partly** generated: its `sea_starts` block is block-replaced by that script (don't hand-edit `sea_starts`), while every other key is hand-authored. `map_data/adjacencies.csv` is created header-only by the script when absent, but its strait/canal rows are hand-authored in the later rendered-map pass — the script never clobbers an existing file. `tools/config/inland_lakes.json` is the inverse case — a hand-authored input, like `tools/registration/seeds/`, that must be edited deliberately (never inferred from a regenerated bitmap) and then regenerated through.
- Preserve determinism: avoid non-seeded randomness or anything that could desync a multiplayer-synchronized mod.
- Never leave a `{{...}}` placeholder or invented content — if `docs/*.log` doesn't confirm an effect/trigger exists, don't use it.
